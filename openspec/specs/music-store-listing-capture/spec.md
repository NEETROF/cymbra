## Requirements
### Requirement: Screenshots are produced by a reproducible command

Store listing screenshots SHALL be generated by a checked-in capture harness driving
the real app, invoked as a single documented command per platform and locale. No
listing screenshot SHALL depend on a manual capture step, on an uncommitted source
edit, or on ad-hoc window placement by the operator.

#### Scenario: Regenerating a set

- **WHEN** an operator runs the documented capture command for a platform and locale
- **THEN** the harness SHALL drive the app through the listing surfaces and write the
  full set of PNGs for that platform and locale into the versioned store assets tree,
  overwriting any previous set

#### Scenario: No source edit required

- **WHEN** macOS screenshots are captured
- **THEN** the window SHALL be sized by the harness at runtime
- **AND** capture SHALL require no edit to `macos/Runner/MainFlutterWindow.swift` or
  any other tracked source file

### Requirement: Captures run against a seeded, presentable state

The harness SHALL place the app in a deterministic state before capturing, so that
repeated runs produce equivalent images and no capture advertises an empty, idle or
failing account.

#### Scenario: An input device is present

- **WHEN** a player surface is captured
- **THEN** the app SHALL report a connected input device
- **AND** no "no MIDI device" indicator SHALL appear in the captured image

#### Scenario: Performance indicators are non-trivial

- **WHEN** a surface showing a live accuracy or progress indicator is captured
- **THEN** that indicator SHALL show a plausible non-zero value seeded by the harness

#### Scenario: Populated content

- **WHEN** a library, course, leaderboard, badge or rewards surface is captured
- **THEN** it SHALL be populated from harness-seeded fixtures rather than whatever a
  live backend happens to hold

#### Scenario: Repeatability

- **WHEN** the same capture command is run twice against the same commit
- **THEN** the two sets SHALL show the same content on every surface

### Requirement: Every shipping locale is covered

Screenshot sets SHALL exist for each locale the listing copy ships in, and the
captured UI language SHALL be that locale.

#### Scenario: A set per locale

- **WHEN** the listing assets are assembled
- **THEN** a complete screenshot set SHALL exist for each shipping locale, stored so
  that the locale of any image is unambiguous from its path

#### Scenario: Locale is driven by the harness

- **WHEN** the harness captures a given locale
- **THEN** it SHALL force the app's display language for that run
- **AND** it SHALL NOT depend on the device language or on the account's stored
  language preference

### Requirement: Sets match each store's current size classes

Committed screenshots SHALL match the pixel dimensions and ratio constraints that the
target store currently requires, and those dimensions SHALL be asserted rather than
assumed from the capture device.

#### Scenario: Apple size classes

- **WHEN** App Store screenshots are captured
- **THEN** the iPhone set SHALL match the display class App Store Connect currently
  requires for iPhone, and the iPad set the class it currently requires for iPad
- **AND** the Mac set SHALL match one of the accepted Mac screenshot sizes

#### Scenario: Google Play constraints

- **WHEN** Google Play phone screenshots are captured
- **THEN** each image's longer side SHALL be at most twice its shorter side
- **AND** the set SHALL meet Play's recommended ratio and minimum resolution for
  recommendation surfaces

#### Scenario: Dimensions are verified

- **WHEN** a capture run completes
- **THEN** the harness SHALL fail if any produced image does not match the declared
  dimensions for its platform, rather than emitting an off-size image

#### Scenario: Format

- **WHEN** an image is committed as a listing asset
- **THEN** it SHALL carry no alpha channel or transparency

### Requirement: Sets cover the app's headline surfaces

A screenshot set SHALL show the surfaces the listing copy sells, so the listing does
not under-represent shipped functionality.

#### Scenario: Surface coverage

- **WHEN** a set is produced for a platform
- **THEN** it SHALL include the score library, the falling-notes player, the staff
  view, and the surfaces backing the listing copy's headline claims, within the
  per-store maximum image count

#### Scenario: Drift is visible

- **WHEN** a shipped feature has no corresponding capture
- **THEN** the store assets documentation SHALL record which surfaces the current sets
  cover, so the gap is auditable without opening every image
