# Design — releasing Lingua from a tag

## D1 — Two components, not one

`lingua-extension` and `lingua-apple` are versioned separately.

They ship to different stores, on different cadences, and their versions answer different questions: the Apple app's is what a user reads in the App Store, the extension's is what Chrome shows in `chrome://extensions` and what AMO refuses to accept twice. A shared version would force a no-op App Store submission — review included — every time a Chromium-only fix moved the extension.

The repo's release-please config sets `separate-pull-requests: false`, so both still arrive in one Release PR; only the tags and the changelogs are separate.

**Rejected**: one `lingua` component. It reads as simpler until the first Chromium hotfix, which would have to be shipped through Apple review to keep the numbers honest.

## D2 — The extension's version lives in `package.json`, mirrored into the manifest

release-please's `node` strategy bumps `package.json`. The manifest — the one `manifest.json` that `build.mjs` folds into three variants — is bumped by the same run through `extra-files` (`$.version`).

So the mirror is written by release-please, not by a human, and `build.mjs` needs no change: it already passes `version` through untouched to each variant.

A guard in `lingua-extension-check` fails when the two disagree. It exists for the case release-please is not in the loop — a hand edit to one of the files — because the failure it prevents is silent: a Chromium zip that reports a version the changelog never mentions.

**Rejected**: the manifest as the source. It is the file a browser reads, which makes it tempting, but release-please would then need `extra-files` in the other direction plus a `node` package with a version it does not own; and the manifest is already rewritten per variant, which is one rewrite too many to also be the source of truth.

## D3 — The version has to be a shape Chrome accepts

Chrome's manifest `version` is one to four dot-separated integers, each at most 65535, with no leading zeros and **no pre-release suffix**. SemVer's `1.2.0-rc.1` is rejected at upload.

The release workflow therefore refuses a version that is not three plain integers, before it builds anything. This is a guard rather than a transformation on purpose: silently dropping a `-rc.1` would publish a build the tag says is a candidate.

## D4 — "Published" means "submitted for review"

Both stores review a new version before users get it, and a first submission is reviewed by a human. The workflow's contract stops at the store having accepted the upload: the job's summary says the version is in review, and it does not poll for approval.

This matters for what failure means. A rejected review is not a failed workflow — it arrives days later, by email, and is answered in the dashboard. A workflow that claimed to have "released" would make that state invisible.

## D5 — AMO needs the source, and `web-ext` can carry it

Mozilla requires a source-code submission when the reviewed code was generated by a build step. Lingua's is twice over: an esbuild bundle, and a `.wasm` compiled from Rust.

`web-ext sign --channel listed --upload-source-code <archive>` takes that archive, so one command still does the whole submission. The archive is built from the checkout: the extension's sources, the crates the wasm comes from, and the build instructions a reviewer follows (`yarn install --immutable`, `yarn gen:wasm`, `yarn gen:proto`, `yarn build:firefox`).

The pack (`assets/pack.lingua`, tens of megabytes, generated from a public corpus) is **not** in the source archive: it is data, not code, and `scripts/lingua-data/build.sh` rebuilds it. The instructions say so, because a reviewer who cannot reproduce a file blocks the version.

**Rejected**: the unlisted channel, which needs no review and no source. It would also forfeit AMO search and the Firefox Android install path, which is the only way the extension reaches an Android phone.

## D6 — The Apple version comes from `version.txt`, not from the project file

`MARKETING_VERSION = 1.0` appears eight times in `project.pbxproj`. The lane already passes `CURRENT_PROJECT_VERSION` on the `xcodebuild` command line, and one more setting costs nothing there.

Keeping the release version out of the committed project matters more than usual here: CI already rewrites that file for App Store signing (`tool/ci_release_signing.py`). A second CI-owned edit in the same file is a merge conflict waiting for the next signing change.

release-please's `simple` strategy — the one the backend already uses — maintains `version.txt`. On a tag the lane asserts the file and the tag agree, so a tag pushed by hand cannot ship a version the changelog does not describe.

## D7 — Build numbers stay the run number

`IOS_BUILD = run×10`, `MACOS_BUILD = run×10+1`. App Store Connect only requires build numbers to increase within a version across the shared iOS/macOS record, which the run number does by construction — and it survives a dispatch, which a version-derived counter would not.

## D8 — The two versions are independent, and the safari variant follows the app

The Apple lane builds the safari variant from the commit it checks out, so an Apple release ships whatever extension source that commit holds — carrying the extension's version in its bundled manifest, where nothing reads it.

Nobody should read the two version numbers as a matched pair. `lingua-extension-v1.4.0` and `lingua-apple-v1.1.0` can describe the same code, and usually will.

## D9 — The first Release PR must not replay the whole history

release-please assigns a commit to a component by the paths it touches, and neither component has a tag yet. Left alone, the first Release PR would fold every Lingua commit since the first line of the extension — the entire dogfooding pass — into one changelog, and pick a version from it.

The components are therefore seeded in `.release-please-manifest.json` at the version the tree already carries, and the history is cut at the commit that introduces them. The first Release PR is read before it is merged; that is a task, not a hope, because this is the one run where the cut cannot be checked by a test.

## D10 — The first published version is forced, and the forcing is temporary

The extension has never shipped, so release-please's computed `0.2.0` would be its debut on
two stores. `1.0.0` is the version a first public release should carry, and that is a product
decision, not something the commit history can derive.

The mechanism is `release-as` on the component in `release-please-config.json`. The intended
one — a `Release-As:` footer on a commit touching only that component's path — was tried and
lost: this repository squash-merges, and the footer has to survive into the squash commit's
body, which is assembled from the pull request rather than from the branch. It did not.

`release-as` is **sticky**: left in place it pins every later release to 1.0.0, which is worse
than the problem it solves, and the failure is quiet — a Release PR that keeps proposing a
version already tagged. Its removal is therefore task 5.6, not a note: the change cannot be
archived while a task is open, so the repository itself holds the reminder.

## D11 — The version has one home, and it is not the manifest

`package.json` holds the version; `build.mjs` stamps it onto each variant's manifest at build
time. `manifest.json` carries no `version` at all, so there is nothing to disagree with.

D2 said the opposite — release-please would mirror the value into `manifest.json` through
`extra-files` — and the first Release PR showed why that was wrong. release-please's JSON
updater does not edit one value: it re-serialises the whole file in its own style, expanding
every array, and the extension's Prettier gate refused the result. Every future Release PR
would have failed the same way.

Ignoring the file in Prettier would have hidden the symptom and kept the real defect: two
files holding one value. `build.mjs` already rewrites the manifest three times per build —
deleting keys, adding `host_permissions`, adding `key` for Chromium — so stamping the version
there costs one line and removes the second source entirely.

The guard changes shape with it: instead of "do the two files agree", `yarn check:version` now
asks "is the version a shape the stores accept" and "has `manifest.json` grown a `version`
back". The second half matters because a stale copy there would win over the stamp.

`CHANGELOG.md` stays out of Prettier's way too — it is release-please's, in release-please's
style, exactly as `apps/back-office` already declares.

## D12 — A release is not a deployment

A `lingua-extension-v*` tag builds every variant and attaches the two distributable packages
to its GitHub Release. It submits nothing.

Submitting is a separate dispatch of the same workflow, naming that tag and ticking `publish`.

Two reasons, and the second is the one that decided it:

- **Merging a Release PR must not put a version in front of readers.** The merge is a
  versioning act; a store submission is a product decision, and the person making it should be
  the person choosing the moment.
- **A merge must not go red for a reason that has nothing to do with the merge.** Store
  credentials live outside the repository and arrive on their own schedule. With publication
  on the tag, merging the Release PR before they existed would have failed the run and left a
  red cross on a release tag, recoverable only by re-running that exact run — a recovery path
  nobody would guess.

This is the shape `lingua-apple-release` already has, where delivery is an explicit input
rather than a side effect, and it is why the safari variant was never published from here.
